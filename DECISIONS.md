# Архитектурные решения

## Формат записи ADR

Каждая запись содержит номер, дату, статус и связанные требования, затем:

- **Контекст:** исходная проблема, ограничения и источники решения.
- **Решение:** что именно меняется и на каком основании.
- **Последствия:** влияние на функции, проверки и оставшиеся обязательства.
- **Как откатить или обновить:** конкретные условия и действия для пересмотра.

Если решение принято владельцем, записать его ответ. Если оно следует из
проверенного документа, указать источник и отличать факт от инженерного выбора.

## ADR-001. GitHub Pages на текущем этапе

- Дата: 2026-10-04.
- Статус: принято по прямому указанию владельца «пока в пейджес».
- Связанные требования: `spec.md §4.1`, `§11.1`, `§12`; вопрос Q1.

### Контекст

Приветственная страница уже опубликована на GitHub Pages. Спецификация предполагает
Cloudflare Pages и Worker с API на том же домене. Владелец выбрал GitHub Pages
для текущего этапа разработки.

### Решение

Статическую часть тренажёра собирать с помощью Astro и размещать на GitHub Pages.
При настройке проекта учитывать адрес `https://exy100.github.io/test-oge-app/`
и префикс `/test-oge-app/` для страниц, ресурсов и клиентской навигации.
Способ размещения серверной части ИИ выбрать отдельно перед её подключением.

### Последствия

GitHub Pages обслуживает статические файлы; Worker там не исполняется.
Файл Cloudflare `_headers` не задаёт заголовки ответа GitHub Pages. Поэтому нельзя
объявлять требования к API на том же домене и всем заголовкам безопасности
выполненными на GitHub Pages. Их реализация и проверка остаются отдельными задачами.
Ключ OpenRouter по-прежнему должен храниться только на сервере.

### Как вернуться к исходной архитектуре

Перед переносом настроить Cloudflare Pages и домен, изменить базовый путь сборки,
проверить ссылки и ресурсы, подключить Worker на `/api/*`, проверить заголовки и
работу приложения. Переезд и отключение существующего сайта согласовать отдельно.

## ADR-002. Распределение потока 50/50

- Дата: 2026-10-04.
- Статус: принято владельцем («нормально - вперед» в ответ на предложение 50/50).
- Связанные требования: `spec.md §9.4`, `tasks.md T4.1`; вопрос Q2.

### Контекст

Исходное требование минимум 5 % на каждый выбранный номер невыполнимо при выборе
всех 25 номеров. Нижняя граница `min(5 %, 1/N)` убирала бы адаптивность при N >= 20.

### Решение

Половину вероятности распределять равномерно между выбранными номерами,
половину — пропорционально частоте ошибок по этим номерам. Для N номеров и
весов ошибок wᵢ при их положительной сумме:

`pᵢ = 0.5 / N + 0.5 × wᵢ / Σw`, где `wᵢ = 1 − точностьᵢ`.

При отсутствии статистики либо нулевой сумме весов выбирать равномерно.
Одинаковые веса также дают равномерное распределение. Это вероятности следующего
случайного выбора, а не обещание точного количества задач в короткой сессии.
Расписание отдельной очереди повторения ошибок (3/10/30) сохраняется.

### Последствия

Все выбранные номера продолжают встречаться, а слабые темы получают больший вес.
При N = 16 каждый номер имеет нижнюю долю 3.125 % (текущий предмет — информатика). Новый минимум заменяет 5 %
в спецификации и приёмочных проверках T4.1. Реализация и тесты относятся к Фазе 4.

### Как изменить решение

При изменении доли равномерного выбора совместно обновить спецификацию, критерии
T4.1, реализацию и тесты. Возврат к фиксированным 5 % требует ограничения N <= 20
и отдельного согласования с владельцем.

## ADR-004. Информатика — первый предмет

- Дата фиксации: 2026-10-05.
- Статус: принято по прямому указанию владельца «сначала для информатики делаем сайт».

### Контекст

Фаза подготовки математики завершилась в коммите `3d18075`. Владелец изменил
очерёдность предметов до начала реализации приложения.

### Решение

Текущий проект целиком ориентировать на ОГЭ по информатике. Предыдущие девять
документов сохранены побайтово в `docs/archive/mathematics/`. Активные spec/tasks,
модель данных, шкала, типы ответов, планы уроков, интерактивы, ИИ и статусы
пересмотрены под 16 номеров, 150 минут и максимум 21 балл.

Предметный объём: 45 уроков по 14 разделам информатики, 18 двумерных интерактивов,
5 трёхмерных учебных игр, 58 структурных подтипов генераторов и 24 кураторских
набора для двух альтернатив №13. Это проектные минимумы, не нормы ФИПИ.
Математические банки, 25 номеров, таймер 235 минут и геометрический порог в новый
предмет не входят. Общие требования приватности, доступности, детерминизма,
тестов, производительности и безопасности сохраняются.

### Последствия

Нужны файловые наборы ZIP/ODF, слова и буквенные последовательности, интерпретатор
«Робота», программирование, критерии на 3 балла для №14. Появились отдельные
задачи T2.10 и T2.11. Генератор файлов должен создавать реальные форматы,
а не менять расширение текстового файла. Минимумы математики не считаются
достижениями информатики, старые отчёты не выдаются за готовность нового приложения.

Сохраняются GitHub Pages и схема потока 50/50. Пример для всех 16 номеров:
нижняя вероятность каждого — 3.125 %. №13.1/13.2 считаются одним номером.

### Как вернуться к математике

Создать отдельный согласованный этап из архива, обновить официальную сверку
и оценить повторное использование общих компонентов. Не заменять активные
документы математическими без нового указания владельца.

## ADR-005. Рабочие настройки первой версии практики

- Дата: 2026-10-05.
- Статус: рабочий выбор агента; вопросы о языке и офисных редакторах заданы,
  ответы владельца пока не получены. Это не утверждение о пользовательском согласии.

### Контекст

Информатика содержит файловые работы и программирование. Их способ тренировки
в исходном математическом задании не описан. Приёмка структуры экзамена при этом
не зависит от выбора конкретного языка или офисного приложения.

### Решение

Основной учебный язык — Python 3. Офисная практика — скачиваемые наборы,
инструкции для LibreOffice, эталоны и самооценка по критериям. Для «Робота» —
локальный браузерный интерпретатор. Для Python — редактор, выгрузка исходника,
тестовые данные и инструкция запуска в локальной среде ученика.

### Последствия

GitHub Pages остаётся достаточным для статического интерфейса и файлов.
Полная офисная среда и исполнение произвольного Python в браузере не объявляются
реализованными возможностями. Учебные интерактивы отдельных операций обязательны.
Эталоны Python запускаются в среде разработки; это отличается от исполнения
пользовательского кода на сайте. ИИ не получает офисные файлы и не выдумывает
оценку их содержимого. Выбор библиотек ZIP/ODF оформить отдельной записью до установки.

### Как изменить решение

При ответе владельца обновить spec §1, §3.5, задачи практики и соответствующие
проверки. Для встроенных редакторов/исполнителя Python отдельно определить
ограничения, безопасность, производительность и зависимости до их реализации.

## ADR-006. Основа Astro и порядок подключения инструментов

- Дата: 2026-10-05. Инженерное решение для T1.1.

### Контекст

T1.1 требует рабочую команду verify, а предметные проверки описаны в следующей
задаче T1.2. GitHub Pages уже публикует main / (root), без отдельной сборки Astro.
Изменение исходников не должно оставлять сайт с неработающими путями ресурсов.

### Решение

- Node 24 LTS зафиксирован в `.nvmrc`; зависимости и lock-файл фиксируют версии.
  TypeScript 6.0.3 выбран по совместимости с Astro Check и typescript-eslint;
  переход на TypeScript 7 выполняется после поддержки обоими инструментами.
- На T1.1 verify выполняет настоящие lint, format check, typecheck, unit и build.
  T1.2 добавляет check:forbidden и check:coverage; пустые успешные команды не создаются.
  Полный состав verify из spec §17 обязателен к Gate 1.
- Сборка находится в dist. `npm run pages:prepare` копирует только готовую главную
  страницу, favicon, `.nojekyll` и `_astro` в корень. Эти результаты временно входят
  в коммит, чтобы существующая публикация main / (root) продолжала работать.
  Скрипт отклоняет неизвестные файлы dist, а не теряет новые страницы молча.
  Автоматизация и переход к публикации артефакта сборки относятся к T1.3.
- ESLint Astro, Prettier Astro, Astro Check, определения типов, Vite, globals и
  eslint-config-prettier — инструменты интеграции уже утверждённого стека;
  они не добавляют клиентские запросы или сторонние сервисы.
- Playwright поддерживает стандартные браузеры и явный путь к системному Chromium
  для облачной среды. Проверка только Chromium не выдаётся за прогон Firefox/WebKit.
- `dev` и `preview` используют `--ignore-lock`: Astro 7 автоматически переводит
  сервер в фон при обнаружении агента. Явный foreground необходим тестовому runner'у
  для управления запуском/остановкой и изоляции разных портов.

### Исправления зависимостей Lighthouse CI

У последнего Lighthouse CI 0.15.1 зафиксирован старый Lighthouse 12.6.1.
Первый `npm audit` нашёл 11 high, 1 moderate, 2 low в цепочке его инструментов.
Применены точные overrides: Lighthouse 13.5.0 (с актуальным Puppeteer без
уязвимого extract-zip), basic-ftp 6.2.2, tmp 0.2.7 и uuid 11.1.1.
UUID 11 сохраняет CommonJS API, используемый LHCI. Это зависимости разработки;
совместимость проверяется реальным `npm run lh`, а не только разрешением lock-файла.
Повторный audit после установки: 0 vulnerabilities. При обновлении LHCI overrides
удаляются только после повторного audit и прогона Lighthouse с прежними порогами.

### Последствия и откат

Исходник главной страницы — `src/pages/index.astro`, текст — MDX. Корневой index.html
не редактируется вручную. Временно изменён только промежуточный состав verify,
критерии завершения фазы сохранены. Для отката использовать прежнюю статичную
страницу из Git; для перехода к Actions согласованно изменить источник Pages,
workflow и удалить только сгенерированные файлы из корня.
