# Модель данных T2.2

Схемы экспортируются из `src/core/schemas/index.ts`, типы — из
`src/core/types.ts`. Zod 4.6.5 — прямая зависимость из стека spec §4.1,
в той же версии, что уже использует Astro. Типы получаются через `z.infer`:
нет двух вручную синхронизируемых описаний одной структуры.

Все объекты строгие: неизвестные поля отклоняются, а не молча удаляются.
Нет преобразования строк в числа, нормализации ответов или автоматического
исправления путей. `parse` возвращает проверенную копию либо ZodError с путём
ошибки; `safeParse` даёт результат без исключения. Это схемы внутренних
канонических данных; послабления при вводе учеником относятся к T2.4.

## Задания и ответы

Реализованы все именованные типы spec §5: TaskNumber, Score, AnswerType,
ArtifactKind, CorrectAnswer, GradingCriteria, TaskInstance, FigureSpec,
DatasetManifest, PracticeEvidence, Variant. Добавлен контракт Generator из §6.1.

- `CorrectAnswer.type`: integer, word, sequence, artifact. Целый ответ хранится
  десятичной строкой без ограничения точностью Number, без плюса, ведущих нулей
  и отрицательного нуля. Для word/sequence правила регистра обязательны.
  Sequence проверяет заданный алфавит и сохраняет ведущие нули.
- `TaskInstance` сохраняет поля spec §5. Обязательны три подсказки, минимум три
  шага решения, непустые условие и тема. Seed может быть пустой строкой, как в RNG.
- №1–10 — часть 1; №11–16 — часть 2. Краткий ответ применяется к №1–12.
  Практические артефакты №13–16 обязаны соответствовать номеру: presentation
  либо document, spreadsheet, robot, program соответственно.
- Только у №13 есть обязательная variant13. У №13/15/16 максимум критериев 2,
  у №14 — 3. Каждый уровень от 0 до max описан ровно один раз, порядок свободный.
  Эти правила следуют проверенному проекту экзамена: docs/exam-format.md.
- `commonMistakes` допускает пустой список: spec §6.2 требует две ошибки там,
  где они применимы. Применимость и содержательную корректность проверяют
  генераторы и методический аудит, а не форма JSON.

## Фигуры

У всех фигур дискриминатор `kind` и обязательное текстовое `description`.
Это данные для будущего рендерера T2.7, не SVG/HTML. Представления полей
конкретизируют словесный перечень spec §5:

| kind | Поля и инварианты |
|---|---|
| weighted-graph | nodes `{id,label}`, edges `{from,to,weight}`; вес положителен; рёбра неориентированные |
| directed-graph | nodes и edges `{from,to}`; направление существенно |
| table | columns и rows строк/чисел; одинаковая ширина строк |
| logic-circuit | nodes input/not/and/or/xor, output; входы ссылаются на предшествующие элементы |
| place-value | base 2–36, digits слева направо; каждая цифра меньше основания |
| code-table | entries `{symbol,code}`; уникальные символы и двоичные коды |
| file-tree | плоские entries file/directory с относительным path; у файла size; родительский каталог существует |
| network-address | protocol http/https/ftp, host без протокола и пути, относительный path ресурса |
| robot-field | rows, columns, start, painted, targets, walls между соседними клетками |

У графов уникальные id, существующие концы рёбер, нет петель и повторных рёбер.
Логическая схема записана в порядке вычисления: это исключает циклы.
Координаты Робота начинаются с нуля; внешние границы заданы размером поля,
внутренние стены — парами соседних клеток. Повторы стен и клеток отклоняются.
Все числовые данные конечны и не равны отрицательному нулю.
Пересечения подписей, однозначность задачи и вычисление ответа проверяются
при рендеринге и в соответствующем генераторе. Кодовая таблица не обязана
быть префиксной: это свойство конкретного задания, а не всех схем кодирования.

## Файлы

`DatasetManifest.kind`: generated (`generatorId`) или curated (`author`).
Обе ветки содержат id, seed, generatorVersion и непустой files.
Каждый файл: path, format, size в байтах, sha256 (64 строчные hex-цифры), license.
Поддержаны txt/csv/json/odt/odp/ods/zip/png/svg/py/kum; расширение совпадает
с форматом. Пути уникальны, размеры — неотрицательные безопасные целые.

Относительный путь не содержит пустых сегментов, `.`/`..`, обратной косой черты,
двоеточия, управляющих символов, query/hash и percent-encoding. Последний
запрещён целиком, чтобы повторное декодирование не открывало traversal.
Кириллица и пробелы внутри имени допустимы; пробелы на границах сегмента — нет.

Схема проверяет описание файлов. Реальное содержимое, совпадение хеша/размера,
ZIP/ODF, лимиты наборов и открытие в LibreOffice относятся к T2.10;
валидный манифест сам по себе не доказывает наличие корректного файла.

## Практика и варианты

`PracticeEvidence.kind` соответствует пяти видам артефактов. Общие поля:
taskId, criteriaAnswers `{criterionScore,answer}`, необязательная selfAssessment
и принятая assessment `{source,score}`. criterionScore адресует уровень
GradingCriteria; повтор уровня запрещён. Пустой ответ допустим в черновике.

У robot/program также code и localRuns: testId, input, output, status
(completed/error/cancelled/limit), origin строго userLocal. Это записи
пользовательского запуска, не официальный вердикт и не подтверждённый сервером
результат. Поле verdict не допускается.

Баллы не превышают максимум вида работы. Источник self требует совпадения
с самооценкой; aiAccepted допустим только для robot/program. Для офисных файлов
ИИ даёт помощь по критериям, а не балл (spec §11.6). Схема формы не подтверждает
правильность оценки или факт согласия пользователя: это обязанности будущих
сценариев работы с хранилищем и ИИ.

`Variant.kind`: generated с seed или fixed. У обоих id и ровно 16 TaskInstance:
по одному каждого номера, уникальные id, сумма максимумов 21. Порядок массива
не ограничен; экзаменационный порядок задаёт будущий сборщик. Альтернатива
№13 находится внутри единственного задания №13.

## Граница генератора и проверки

`validateGeneratedTask(generator, seed)` в `src/core/generators/harness.ts`
вызывает generate, разбирает результат через TaskInstanceSchema, проверяет
совпадение generatorId/taskNumber/subtype/seed и вызывает независимый verify.
Нарушение схемы останавливает проверку до вызова verify.

Тестовый генератор реально переводит байты в биты и проходит эту границу на
500 seed с проверкой повторяемости. Намеренно испорченные версии отклоняются.
Он существует только в тесте и не считается подтипом продуктового банка.
Примеры всех моделей проверяются TypeScript через satisfies и при исполнении
через схемы; отрицательные случаи покрывают межполевые правила и опасные пути.

Полный property-харнесс, реестр, золотые снапшоты, проверка фигур/файлов/KaTeX
и интерфейс просмотра генераторов — T2.9. Схемы границ storage/URL/Worker будут
подключаться при реализации соответствующих задач; они здесь не объявлены
готовыми. Команда проверки текущего шага: `npm run verify`.
