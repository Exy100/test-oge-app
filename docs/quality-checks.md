# Проверки качества и полноты

`npm run verify` выполняет lint, форматирование, проверку типов, unit-тесты,
check:forbidden, check:coverage и сборку. Скрипты не изменяют исходники.
Версии парсеров зафиксированы в package-lock; Node 24 читает TS-реестры напрямую.

## Запуск и фазы

```bash
npm run check:forbidden
npm run check:coverage
npm run check:coverage -- --phase=3
npm run check:coverage -- --phase=7
npm run check:coverage -- --phase=8
npm run check:coverage -- --phase=final
```

Числовые фазы 0–10 накопительные; `final` означает 10. Неизвестные, повторённые
или некорректные аргументы дают ненулевой код, а не подменяются текущей фазой.
Без аргумента применяется `currentPhase` из coverage.config.ts.

| С какой фазы обязателен объём | Проверка |
|---|---|
| 3 | По 4 подтипа для №1–10, по 3 для №11–12, по 4 для №14–16: всего ≥58 |
| 3 | По 12 авторских наборов презентаций и документов для альтернатив №13 |
| 3 | ≥10 фиксированных вариантов, обязательно V01–V10, разные seed |
| 7 | ≥45 уроков, все 14 разделов со своими минимумами, блоки каждого урока |
| 8 | Все 18 обязательных 2D-интерактивов и 5 3D-игр, ≥3 уникальных уровня в каждой игре |
| 8 | Во всех уроках настоящие зарегистрированные интерактивы, без временных замен |

До срока требование выводится с настоящим количеством и пометкой «обязательно с
фазы N». Отсутствующий будущий реестр означает ноль. Некорректный уже существующий
реестр или урок вызывает ошибку на любой фазе. Файлы в docs/archive и приветствие
src/content/welcome.mdx не увеличивают учебное покрытие.

`currentPhase` не понижать ниже уже принятого этапа. При работе внутри новой фазы
сохранять прежний порог, а на её gate запускать явный `--phase=N`. После успешного
gate повысить currentPhase до N. Сейчас установлен 1: это порог проверки объёма,
а не заявление о прохождении всего Gate 1. Таким образом, промежуточный коммит
нового генератора не требует всех остальных генераторов будущей фазы, но её gate
обязательно требует полный объём.

## Реестры — контракт для следующих задач

Пути заданы в `coverage.config.ts`. Адаптер импортирует реальные доверенные
модули проекта; в них нельзя выполнять сетевые запросы или побочные действия
при импорте. Внутренние импорты чистого TS используют явное расширение `.ts`,
совместимое с Node 24. Отдельные числа покрытия или дублирующие JSON-сводки не читаются.
Символические ссылки реестров и выход за пределы проекта отклоняются.

| Путь | Именованный экспорт | Что считается |
|---|---|---|
| src/core/generators/index.ts | `generators` | Массив Generator из spec §6.1: id, taskNumber, subtype, функции generate/verify. Уникальные пары номер/подтип, а не число файлов |
| src/core/banks/index.ts | `bankTasks` | Массив TaskInstance для №13: id, variant13, datasetId, artifact-ответ с kind/referenceId, criteria.max=2. Уникальные наборы отдельно по двум альтернативам |
| src/core/variants/index.ts | `fixedVariants`, `buildVariant` | Массив записей `{id, seed}` и настоящая функция сборщика. Уникальные id и seed, все V01–V10 |
| src/interactives/index.ts | `interactives` | Массив `{id, kind, load, levels?}`: kind 2d/3d, функция ленивой загрузки, у 3D массив уровней с уникальными id |

Все идентификаторы непустые и уникальные в своём реестре. Идентификаторы каталога
интерактивов закреплены в coverage.config.ts в том же порядке, что spec §10.3.
Повторное использование интерактива в нескольких уроках не создаёт новый интерактив.
Новый id генератора с прежним номером/подтипом не создаёт новый подтип. Один datasetId
не становится двумя наборами одной альтернативы из-за смены id задачи.

Скрипт не вызывает generate, verify, buildVariant и load; их корректность проверяется
предметными тестами и браузером на соответствующем этапе. Он проверяет зарегистрированный
объём и структуру, не доказательство работоспособности каждой реализации. Полные zod-схемы
модели и проверка ZIP/ODF остаются задачами T2.2, T2.10 и T3; минимальные поля адаптера
не заменяют эти схемы.

## Уроки MDX

Источник: `src/content/lessons/**/*.mdx`. Frontmatter — YAML с уникальными ключами:

- `id`, `title`: непустые строки, id уникален в коллекции;
- `section`: i1–i14 (И1–И14 из spec §10.1);
- `taskNumbers`: непустой список уникальных целых номеров 1–16;
- `readingMinutes`: положительное целое число;
- `prerequisites`: список уникальных id существующих уроков, без ссылки на себя;
  пустой список допустим.

Ни YAML, ни выражения из урока не исполняются. Тело разбирается MDX-парсером.
Обязательные блоки верхнего уровня идут в таком порядке:

| Блок | Минимум внутри |
|---|---|
| LessonHeader | Метаданные урока из frontmatter |
| Motivation | Непустое объяснение назначения темы |
| Theory | ≥2 Figure или svg; вложенный svg внутри Figure не считается второй визуализацией |
| Interactive | ≥1 компонент с буквальным строковым id из реестра |
| Examples | ≥3 Example |
| Mistakes | ≥3 Mistake |
| Quiz | ≥5 Question |
| StreamLink | Компонент перехода к потоку |
| CheatSheet | Непустое содержимое шпаргалки |

Блоки, кроме Interactive, не повторяются. Дополнительные TOC/LessonNav не меняют
этот порядок. Поддерживаются и многострочные компоненты, и однострочные JSX-блоки,
которые MDX помещает внутрь абзаца. Названия в fenced code, комментариях и строковых
выражениях не считаются компонентами. Динамические массивы JSX не являются способом
объявления количества: Example/Mistake/Question должны присутствовать как реальные
узлы исходного MDX, данные можно передавать им через свойства.

До gate 8 допускается `InteractiveFallback` на месте Interactive с id из обязательного
планового каталога и реальной Figure/svg внутри, как разрешено T7.4–T7.10. Скрипт выводит
каждую такую пару урок → интерактив с файлом/строкой. При работе над фазой 7 автор переносит
полный список в STATUS.md; к T8.10 он должен быть пуст. Начиная с фазы 8 любая такая замена
даёт ошибку даже при наличии живого интерактива в реестре.

Минимумы блоков не доказывают правильность текста, возрастающую сложность примеров,
доступность, работоспособность ссылок и локальной проверки теста. Это предметные проверки,
схема коллекции T7.1, рендер компонентов и e2e.

## Запрещённые конструкции

check:forbidden читает текстовые исходники в src, worker/src и tests. Формат ошибки:
`путь:строка: правило: объяснение`; найденное значение секрета не печатается.
Код возврата 1 при находках, ошибке чтения или недопустимом аргументе.

Проверяются маркеры незавершённости из PROMPT §4 (без учёта регистра и с границами
слов), сокращения вместо кода, not implemented, внешние script/CSS/font-источники,
характерная форма ключа OpenRouter. Для JS/TS дополнительно разбирается синтаксис:
явный any, test/it/describe/bench.only/skip (включая импорт под другим именем),
Math.random в src/core, document.cookie, пустые функции и постоянно пустые компоненты.
В Astro разбираются frontmatter и script, с сохранением исходных номеров строк.

Строки, template- и regex-литералы внутри файлов тестов не проверяются на текстовые
маркеры: в них находятся намеренно отрицательные примеры. Настоящие TODO-комментарии,
only/skip, пустые функции и подавления типов в этих же тестах проверяются.
Реальные API-ключи не допустимы даже в тестовых данных; их отсутствие отдельно
проверяется gitleaks в T1.3 и проверкой dist в T9.3.

`@ts-ignore` запрещён. `@ts-expect-error` допускается только в TypeScript-файле теста с
объяснением; tsc проверяет ожидаемую ошибку и отклоняет неиспользуемую директиву.
`eslint-disable` требует ссылки ADR-NNN в том же комментарии и раздела DECISIONS.md,
который прямо содержит данный путь. Сам сканер не выдаёт разрешение на исключение.

Это автоматизация распознаваемых конструкций, а не замена ревью: произвольную
семантическую подмену данных или замаскированную сетевую активность текстовый сканер
не доказывает. Скрипты, конфигурация и документация проверяются ESLint/типами/тестами
и ревью; они не входят в поиск пользовательских заглушек. Сгенерированные _astro,
dist и отчёты исключены из анализа исходников и TypeScript; src и worker не исключены.
